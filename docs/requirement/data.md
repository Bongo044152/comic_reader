# 資料定義

> `dev.md` 第 4 章的附屬文件。第 1 章是總覽，先讀完它再看後面的資料卡。
>
> 資料庫選型待定（Q-D1），型別以「整數、字串、時間、布林、JSON」這類通用名稱表示。

## 1. 總覽

### 1.1 兩種管理方式

系統的資料依特性分成兩種管理方式：

| 類型 | 特性 | 管理方式 | 例子 |
| --- | --- | --- | --- |
| Metadata | 結構化、體積小、需要查詢與關聯 | 資料庫 | 帳號、漫畫資訊、章節列表、資料夾 |
| 二進位資料 | 體積大、只會整份讀寫、不需要查詢 | 檔案系統 | 章節圖片 |

圖片不放資料庫的原因：

- 大 blob 會經過 buffer pool 與 WAL，拖慢備份。
- 讀圖得經過資料庫連線；檔案系統可以直接 `sendfile`。
- 快取淘汰只要 `unlink`；資料庫需要 `DELETE` 加 vacuum。

資料庫完全不記錄圖片的任何資訊（路徑、頁數、大小）。圖片存不存在、完不完整由檔案系統決定，路徑由 Manga 與 Chapter 的欄位組出。好處是沒有「兩邊要一起刪、對不上」的問題；唯一的單向情況是資料庫記錄被刪後，留下沒人引用的檔案，留給淘汰清理。

另外有兩筆**運行時狀態**不屬於這兩種：登入狀態與 Plugin registry。它們不是要長期保存的內容，集中在第 5 章說明。

### 1.2 資料庫的兩類資料

資料庫裡的資料再依「屬於誰」分成兩類：

| 類別 | 資料 | 特性 |
| --- | --- | --- |
| 使用者相關 | User、Folder、FolderManga | 屬於個別使用者，其他人看不到。API 要檢查資源屬於目前登入者；刪除帳號時連帶刪除 |
| 漫畫資料（共用） | Manga、Chapter | 全體共用。以「來源 + 來源上的 ID」識別同一部漫畫，一位使用者觸發同步，所有人都會看到；只在有人加入書庫時才存在 |

兩類資料靠 **FolderManga** 連起來：哪位使用者的哪個資料夾放了哪部漫畫。

漫畫資料何時可以刪除，由使用者端決定：有多少位使用者把這部漫畫放在書庫（見 [Folder](#folder)）裡，就是它的 ref count，歸零才回收。

### 1.3 資料清單

| 資料 | 類別 | 存放 | 說明 |
| --- | --- | --- | --- |
| [User](#user) | 使用者相關 | 資料庫 | 帳號與密碼雜湊 |
| [Folder](#folder) | 使用者相關 | 資料庫 | 資料夾，書庫是其中一個 |
| [FolderManga](#foldermanga) | 使用者相關 | 資料庫 | 資料夾與漫畫的成員關係 |
| [Manga](#manga) | 漫畫資料（共用） | 資料庫 | 漫畫詳情 |
| [Chapter](#chapter) | 漫畫資料（共用） | 資料庫 | 章節列表 |
| [章節圖片](#章節圖片) | 二進位資料 | 檔案系統 | 每章的圖片檔 |
| [登入狀態](#草稿-登入狀態) | 運行時狀態 | 待定（Q-D3） | 登入後的身分憑證 |
| [Plugin registry](#草稿-plugin-registry) | 運行時狀態 | 記憶體 | 已註冊的 plugin |
### 1.4 規模

資料卡的「規模」欄不估算筆數，只回答這筆資料會不會無限成長、上限由誰保證：

| 分類 | 意義 |
| --- | --- |
| 有界 | 設計上就固定，不會成長 |
| 線性成長 | 隨使用量成長，每筆很小，總量可忽略 |
| 無界 | 不處理就會一直增加，需要明確的上限機制 |

整體設計規模：使用者約 10 位，家用或小團體。各項上限（如章節圖片的空間上限）寫在設定檔，可以透過 Backend Management 修改，也可以直接編輯。規模超過約 10 倍時，要重新評估資料庫選型（Q-D1）與列表 API 是否分頁。

資料庫的資料量比圖片小幾個數量級，需要設限的主要是圖片。

### 1.5 資料卡欄位

每張資料卡依序為：

| 欄位 | 內容 |
| --- | --- |
| 資料名稱 | 這筆資料是什麼 |
| 定義 | 欄位、型別、必填；唯一鍵 |
| 獲取 | 從哪來（使用者輸入、plugin 回傳、計算得出） |
| 存取 | 存哪、怎麼讀、怎麼寫 |
| 關聯 | 與其他資料的關係 |
| 生命週期 | 何時建立、更新、刪除 |
| 一致性 | 驗證者、唯一性、重複寫入的處理 |
| 敏感度 | 隱私與保護方式（如不可寫入 log） |
| 權限 | 誰可以操作這筆資料（讀、寫、刪） |
| 規模 | 是否無限成長、上限由誰保證 |
| NOTE | 選填。特殊行為與補充，只在需要時出現 |

## 2. 資料庫：使用者相關資料

這一類資料屬於個別使用者，彼此的關係是：User 擁有多個 Folder；Folder 透過 FolderManga 指向共用的 Manga。

### User

**資料名稱**：使用者帳號。

**定義**

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `id` | 整數 | 是 | 主鍵 |
| `username` | 字串 | 是 | 唯一 |
| `password_hash` | 字串 | 是 | 密碼雜湊，不存明文 |
| `created_at` | 時間 | 是 | |

唯一鍵：`id`、`username`。

**獲取**：由管理者經 Backend Management（CLI）建立；V1 沒有註冊功能。

**存取**：資料庫。登入時由 Backend 讀取並比對雜湊；建立、刪除只由 Backend Management 寫入。

**關聯**：一對多 Folder。

**生命週期**：由管理者建立；V1 不更新（修改密碼待補）；刪除時 Folder、FolderManga 連帶刪除，並刪除該使用者的 `scratch` 目錄。

**一致性**：`username` 唯一；帳號建立時由 Backend 同時建立該使用者的預設資料夾（書庫）。

**敏感度**：高。`password_hash` 不可出現在任何 API 回應與 log。

**權限**
- 建立、刪除：只有管理者，經 Backend Management。
- 讀取：Backend（登入驗證）；使用者經 API 只能取得自己的 `id` 與 `username`。
- 修改：V1 沒有人可以修改。

**規模**：線性成長，數量由管理者控制（沒有註冊功能）。

### Folder

**資料名稱**：資料夾。預設資料夾（書庫）也是 Folder，用 `is_default` 區分，特殊行為見最後的 NOTE。

**定義**

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `id` | 整數 | 是 | |
| `user_id` | 整數 | 是 | 指向 User |
| `name` | 字串 | 是 | 不可為空 |
| `is_default` | 布林 | 是 | `true` 為書庫 |

唯一鍵：`id`；`(user_id, name)`；`(id, user_id)`（供 FolderManga 參照）。

**獲取**
- 預設資料夾（書庫）：帳號建立時由系統建立，名稱固定為「書庫」。
- 自訂資料夾：使用者輸入名稱建立，或在「加入資料夾」時隱含建立。

**存取**：資料庫。使用者操作時由 Backend 讀寫；API 中 `library` 代表該使用者的預設資料夾。

**關聯**：多對一 User；一對多 FolderManga。

**生命週期**
- 建立：帳號建立（書庫）或使用者建立（自訂）。
- 更新：自訂資料夾可重新命名；書庫不可。
- 刪除：自訂資料夾可刪除，其 FolderManga 連帶刪除，漫畫本身與書庫不受影響；書庫不可刪除；隨 User 連帶刪除。

**一致性**：同一位使用者內名稱不可重複；每位使用者恰有一個 `is_default = true`；建立資料夾並加入漫畫在同一個 transaction 完成。

**敏感度**：中，使用者私有。

**權限**
- 讀、寫、刪：只有擁有者本人，經 API；API 要檢查資源屬於目前登入者，不屬於回 403 或 404。
- 其他使用者與管理者（經 API）都看不到。
- 書庫的限制見 NOTE。

**規模**：線性成長。每位使用者固定一個書庫，自訂資料夾數量沒有上限，但每筆很小。

**NOTE：書庫（`is_default = true`）的特殊行為**
- **身分**：書庫是每位使用者的預設資料夾，不是獨立的資料；每位使用者恰有一個，帳號建立時由系統建立，名稱固定為「書庫」。API 以 `library` 代表它。
- **不可變動**：不可刪除、不可重新命名。
- **成員的前提**：漫畫必須先在書庫，才能放進自訂資料夾。
- **加入漫畫**：使用者「加入漫畫」就是把它放進書庫。
- **移除漫畫**：從書庫移除等於真正刪除這部漫畫，連帶移除其他資料夾中的這部漫畫，並影響 ref count。
- **ref count**：由所有使用者書庫中的 FolderManga 筆數推導。

### FolderManga

**資料名稱**：資料夾與漫畫的成員關係。資料夾只存關係，不存漫畫本身（C-1）。這張表連接「使用者相關」與「漫畫資料（共用）」兩類資料。

**定義**

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `folder_id` | 整數 | 是 | 指向 Folder |
| `user_id` | 整數 | 是 | 與 Folder 的擁有者一致 |
| `manga_id` | 整數 | 是 | 指向 Manga |

唯一鍵：`(folder_id, manga_id)`。

**獲取**：使用者操作產生：加入書庫、加入或移出資料夾。

**存取**：資料庫。書庫與自訂資料夾的成員都存在這裡。索引 `(user_id, manga_id)` 供詳情頁查詢，`(manga_id)` 供 ref count。

**關聯**：多對一 Folder；多對一 Manga。

**生命週期**
- 建立：加入書庫（寫入預設資料夾）、加入自訂資料夾。
- 刪除：移出資料夾；從書庫移除漫畫時，同一個 transaction 內刪除該使用者所有資料夾中的這部漫畫；隨 Folder 或 User 連帶刪除。

**一致性**
- `(folder_id, user_id)` 參照 Folder 的 `(id, user_id)`，確保資料夾與成員屬於同一位使用者。
- 自訂資料夾的成員必須也在書庫內（子集），由資料庫保證：自訂資料夾的成員以外鍵指向同一位使用者書庫中的同一部漫畫，從書庫移除時連帶刪除。外鍵如何指向書庫的那一列，留給資料庫設計階段。
- 重複加入冪等。

**敏感度**：中，使用者私有。

**權限**：讀、寫、刪只有擁有者本人，經 API；檢查方式同 Folder。

**規模**：線性成長，隨書庫漫畫數與資料夾數增加，每筆很小。

## 3. 草稿 資料庫：漫畫資料（共用）

> 附註：具體行為需要 MVP 之後才能確認，本章內容先視為草稿。

這一類資料全體共用，描述「一部漫畫在某個來源上長什麼樣子」，與哪位使用者無關。只有在至少一位使用者把它加入書庫後才會存在於資料庫；搜尋結果與未加入漫畫的同步結果不寫入，所以資料庫裡沒有沒人引用的孤兒。

**ref count**：不另存欄位，由「預設資料夾中有這部漫畫的 FolderManga 筆數」推導，避免兩處不一致。歸零時在同一個 transaction 刪除 Manga，Chapter 連帶刪除。

### Manga

**資料名稱**：漫畫（一個來源上的一部漫畫）。漫畫 id = 漫畫 + 來源，同名漫畫不同來源視為不同條目。

**定義**

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `id` | 整數 | 是 | surrogate id，供資料庫內部外鍵 |
| `source_id` | 字串 | 是 | 來源（plugin / 網站），如 `mangadex` |
| `remote_id` | 字串 | 是 | 漫畫在該來源上的 ID |
| `title` | 字串 | 是 | 漫畫名稱 |
| `cover_url` | 字串 | 是 | 封面網址 |
| `author` | 字串 | 否 | 空值顯示「未知」 |
| `status` | 字串 | 否 | 連載狀態，列舉待定（Q-D9） |
| `region` | 字串 | 否 | |
| `tags` | 字串陣列 | 否 | 儲存方式待定（Q-D9） |
| `summary` | 字串 | 否 | |
| `remote_updated_at` | 時間 | 否 | 來源上的更新日期 |
| `detail_synced_at` | 時間 | 否 | 最近一次詳情同步 |
| `chapters_synced_at` | 時間 | 否 | 最近一次章節同步 |

唯一鍵：`id`；`(source_id, remote_id)`。

為什麼有兩組鍵：

- `(source_id, remote_id)` 是漫畫在外界的身分。`remote_id` 只在單一來源內唯一，不同網站可能撞號，兩欄合起來才能指出哪個網站的哪部漫畫。
- `id` 是資料庫內部用的整數，讓 Chapter、FolderManga 的外鍵短、好 join。

**獲取**
- 必填欄位（`source_id`、`remote_id`、`title`、`cover_url`）：來自 plugin 搜尋結果，在「加入」時帶入。
- 其他欄位：詳情同步時由 plugin 回傳。plugin 沒有的欄位回傳空值。

**存取**：資料庫。讀取：詳情頁、書庫與資料夾列表、本地搜尋。寫入：「加入」建立；詳情同步更新。

**關聯**：一對多 Chapter；經 FolderManga 與 Folder 多對多。

**生命週期**
- 建立：使用者第一次把這部漫畫加入書庫時。
- 更新：詳情同步，且 ref count > 0 才寫入；最短間隔內不重複向來源抓取。
- 刪除：ref count 歸零時，Chapter 連帶刪除。

**一致性**：`(source_id, remote_id)` 唯一，防止同一部漫畫重複入庫；重複「加入」不報錯（冪等）。這筆資料全體共用，一位使用者觸發的同步，所有人都會看到。

**敏感度**：低，全體共用，不含個人資料。

**權限**
- 讀：所有已登入的使用者。
- 寫：只有 Backend（「加入」建立、詳情同步更新），由使用者操作觸發；使用者不能直接編輯欄位。
- 刪：只有 Backend，ref count 歸零時。
- plugin 只回傳 JSON，不碰資料庫。

**規模**：線性成長，隨全體使用者的書庫成長，因共用而少於各人書庫的總和；V1 沒有硬上限，每筆很小。

### Chapter

**資料名稱**：漫畫的章節。

**定義**

| 欄位 | 型別 | 必填 | 說明 |
| --- | --- | --- | --- |
| `id` | 整數 | 是 | |
| `manga_id` | 整數 | 是 | 指向 Manga |
| `remote_id` | 字串 | 是 | 章節在來源上的 ID |
| `title` | 字串 | 是 | 章節標題，不一定是數字 |
| `sort_order` | 整數 | 是 | 排序 |

唯一鍵：`id`；`(manga_id, remote_id)`。

**獲取**：章節同步時由 plugin 回傳章節列表。

**存取**：資料庫。章節同步寫入；詳情頁與閱讀器讀取。

**關聯**：多對一 Manga。

**生命週期**
- 建立與更新：章節同步，且 ref count > 0 才寫入。
- 刪除：隨 Manga 連帶刪除。
- 更新衝突不存狀態：使用者選擇更新時，plugin 執行同步，發現衝突（來源重新編號、刪除章節或換源，C-5）就不自動套用，直接回饋給前端由使用者決定。

**一致性**：`(manga_id, remote_id)` 唯一；章節同步不載入圖片。

**敏感度**：低，全體共用。

**權限**：同 Manga。讀為所有已登入的使用者，寫與刪只有 Backend（章節同步、隨 Manga 刪除）。

**規模**：線性成長，是資料庫中筆數最多的一張表；V1 沒有硬上限。

## 4. 檔案系統：章節圖片

### 章節圖片

**資料名稱**：章節的圖片檔，不入資料庫（原因見 1.1）。

**定義**

| 項目 | 內容 |
| --- | --- |
| 已加入的漫畫 | `/data/{source}/library/{遠端漫畫 id}/{遠端章節 id}/` |
| 未加入的漫畫 | `/data/{source}/scratch/{userId}/{遠端漫畫 id}/{遠端章節 id}/` |
| 頁面檔 | 按頁碼命名，如 `001.jpg` |
| 完成標記 | 章節目錄中的 `manifest.json`，最後寫入 |

唯一鍵：路徑本身。路徑由 `Manga.source_id`、`Manga.remote_id`、`Chapter.remote_id` 組出，不使用資料庫 id，所以漫畫進資料庫之前圖片就能寫入（系統允許閱讀未加入的漫畫）。

例子：`Manga(id=42, source_id=mangadex, remote_id=a1b2c3)` 第 778 話第 1 頁，路徑是 `/data/mangadex/library/a1b2c3/778/001.jpg`，路徑裡沒有 42。第一層是否為來源、目錄名編碼待定（Q-D6）。

**獲取**：plugin 向來源網站抓取，直接寫入共享 volume，不經過 Backend。

**存取**：檔案系統。plugin 只掛自己的來源目錄（讀寫）；Backend 掛整個根目錄，讀取並服務圖片，淘汰時 `unlink`。寫入目標由 Backend 決定：ref count > 0 寫 `library`，否則寫該使用者的 `scratch`。

**關聯**：沒有資料庫外鍵，與 Manga、Chapter 的關係只在路徑。

**生命週期**
- 建立：使用者載入章節且未命中快取時，由 plugin 抓取；寫到同一 mount 內的 `.tmp-*`，完成後 `rename()`，最後寫入 `manifest.json`。
- 更新：強制刷新；檔案不原地修改，只用新檔取代。
- 刪除：`scratch` 每位使用者只保留最近 5 章，超過刪最舊的；刪除帳號時刪除該使用者的 `scratch`；ref count 歸零只刪資料庫記錄，`library` 的檔案留給淘汰清理。

**一致性**：`manifest.json` 存在才代表完整；同一章被多人同時請求時要避免重複下載（見 `dev.md` 備忘「爭奪問題」）；章節是一組檔案，目錄層級的原子性靠 `.tmp-*` 加 `rename()`，同一個 mount。

**敏感度**：`scratch` 是使用者私有，`library` 全體共用。

**權限**
- 寫：只有 plugin，且只能寫自己的來源目錄。
- 讀：使用者只能經 Backend 的 API 讀；`library` 所有已登入的使用者可讀，`scratch` 只給屬主本人（以登入狀態比對）。
- 刪：只有 Backend（淘汰、刪除帳號時），使用者與 plugin 不能刪。

**規模**
- `scratch`：有界，每位使用者只保留最近 5 章。
- `library`：有界，但是唯一會大量佔用磁碟的資料。上限寫在設定檔，超過上限時寫入失敗。設定檔可以透過 Backend Management 修改，也可以直接編輯。

## 5. 草稿 運行時狀態

這兩筆資料不是要長期保存的內容，所以不在資料庫也不在檔案系統。

### 草稿 登入狀態

**資料名稱**：使用者登入後的身分憑證（JWT 或 server-side session）。

**定義**：待定（Q-D3）。

**獲取**：登入成功後由 Backend 簽發。

**存取**：待定。JWT 存在客戶端，session 存在伺服器端（可能需要 Session 表）。

**關聯**：指向 User。

**生命週期**：登入建立，登出清除，過期後回 401。

**一致性**：除登入 API 外，每支 API 都檢查；沒有或過期一律回 401。

**敏感度**：高，不可寫進 log。

**權限**：簽發與驗證只有 Backend；持有者是登入的使用者本人，只能用於自己的請求。

**規模**：有界，同時登入者不超過使用者數。

### 草稿 Plugin registry

**資料名稱**：目前已註冊的 plugin 清單。

**定義**：V1 只定義最小欄位：`source_id`、名稱、位址。plugin 以名稱或 id 識別，不用 IP 當身分，因為 container 重建後 IP 會變。

**獲取**：plugin 啟動後向 Backend 固定位址註冊；V1 認證只檢查來源 IP（同一個內部 network）。

**存取**：Backend 記憶體，不入資料庫。寫入集中在少數函式，內部不含 `await`；更新時整個 entry 換掉，讀的一方視為不可變。

**關聯**：`source_id` 對應 Manga 的 `source_id`，但沒有 Source 表。

**生命週期**：註冊時建立，plugin 重起或移除時更新；掉線後的清理（health check）V1 不處理。Backend 重啟後 registry 清空，等 plugin 重新註冊。

**一致性**：同一個 `source_id` 重複註冊以新的取代。

**敏感度**：中。

**權限**
- 寫：plugin 啟動時註冊；註冊端點只對同 network 的 container 可達，不 publish 到 host。
- 讀：只有 Backend；使用者經「列出已註冊 plugin」的 API 間接取得，不能直接存取。

**規模**：有界，最多約 10 筆。
